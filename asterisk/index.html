How it works

Five pieces, one deployable unit.

Ingestion, normalization, storage, synthesis and the interface ship together as one Docker Compose stack. You point it at an LLM endpoint you already run; everything else is inside the box.

  1. 1
    Ingestion connectors
    A file lands in a watched folder, or is dropped into the UI, with source metadata carried through for later citation.
  2. 2
    Parsing and normalization
    PDF and DOCX convert to Markdown first; everything is chunked by heading or page, source pointer intact.
  3. 3
    Knowledge store
    Postgres with pgvector holds normalized text, a retained copy of the original, and its embedding — updated incrementally.
  4. 4
    Query and synthesis
    The question is embedded, relevant material retrieved, and your own LLM endpoint writes the answer.
  5. 5
    Interface
    Ask, read, verify against sources, and manage what has been ingested.
Data residency

Your material never leaves your infrastructure.

Zero data export to extranet. This is the constraint the system is designed around, not a compliance footnote bolted to the end of a feature list. For a wealth desk, that means client statements, suitability notes and committee minutes stay where your regulator expects them.

On-prem, single-tenant
Each deployment runs entirely inside infrastructure you control — on-prem, or your own cloud account. No vendor-operated shared backend anything depends on.
Bring your own model
Point it at any OpenAI-compatible endpoint already inside your boundary — or run Ornith-1.5, the open-weights model we provide. Either way it never calls a vendor-hosted model.
Embeddings generated locally
Retrieval requires no external call either. The bundled embedding generator has no network-capable dependency at all.
No vendor control plane
Install, upgrade, backup and rollback are procedures your own operations staff run, documented end to end.
Verified, not just claimed
An automated audit inspects every outbound network client in the dependency graph, and a static-scan regression guard runs as part of the normal test suite. A change that violates the boundary fails a test run rather than a customer's trust.
Ingestion

Five ways in, one catalogue.

However material arrives, it converges on the same path — so a question can draw on all of it without you tracking where anything came from.

Watched folder
A host directory or mounted share. Files landing there are picked up on a poll interval you can change while the stack runs.
Upload
Drag and drop into the interface. Same catalogue, same citation metadata.
Attach from the prompt
Attach a file inline and the question stays blocked until the attachment is fully queryable — a stricter, synchronous variant of ingestion.
Audio
Recordings pass through the bundled speech-to-text container before normalization. Dictation uses the same service; a spoken question becomes editable text, never auto-sent.
Email
An IMAP poll brings messages in on the same path as everything else.
Deep mode

An answer you can judge, not just read.

Ask at Quick, Standard or Deep. A Deep answer is stored as its own synthesis record, so it carries actions the lighter modes do not.

A synthesis is a record, not a message
Every Deep answer is stored with the sources behind it and a feedback state — pending until you rule on it. Review goes back and forth: reject with a note, the same sources go back to the model, and the synthesis is rewritten in place for another look. Once you accept it, it stops being a draft and materialises into usable knowledge the next answers can draw on. Nothing is judged by the model on your behalf.
Accepted · retry rewrites it in place
Mark it helpful, or not
Every Deep synthesis starts pending and moves to accepted or rejected on your call. Accepted syntheses inform later answers.
Guided retry
Pick a reason or write a note, and the same sources go back to the model — rewriting that synthesis in place rather than stacking another attempt below it.
Sources drawer
Every citation behind the answer, grouped by document versus what the model inferred by combining passages, each row linking back to where it came from.
Follow-ups and sharing
The synthesis suggests the questions it opens up. Copy link and file download stay on your server; other channels stay visibly disabled until their integration is approved.

Roadmap

What is in progress, and what is next.

Five tranches have shipped and are stable, each verified against a real running stack. These are the things we are working on now and the ones we have decided to do next — tracked in the open rather than implied.

In progress Safer destructive actions
A typed confirmation gate on reset and reindex, and a progress bar while a reindex runs, so a recovery action is never a single unlabelled click.
In progress Per-file state in the composer
Individual progress and status for each attachment in the attach tray, a queue summary line, and a limit of two concurrent indexing jobs.
In progress Answered while indexing
A note on any answer produced while material was still being ingested, with an ask-again control once the queue drains.
In progress End-to-end coverage for Deep mode
Scripted scenarios for the feedback lifecycle, retry, sharing and follow-ups, replacing the live smoke test currently covering them.
Next Multi-user access control
Asterisk is single-user today. Team collaboration and per-user access control are the largest planned addition.
Next Defined success metrics
Numeric targets for citation accuracy, answer latency and upload-to-queryable time, published rather than left implicit.
Next Better confidence scoring
The score is a flat average across retrieved items today, so it moves with the retrieval count. Recalibrating it against real usage is underway.
Next Wider context-window detection
Native probes exist for LM Studio, Ollama, text-generation-webui and LocalAI. Other servers fall back to a generic probe and manual retrieval limits.
